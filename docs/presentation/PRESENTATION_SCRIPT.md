# 나만의 냉장고 발표 대본

- 발표 시간: 5분
- 슬라이드: 10장
- 편집 원본: `PRESENTATION_SOURCE.pptx`
- 제출 파일: 편집 원본을 PDF로 내보낸 뒤 저장소 루트에 `PRESENTATION.pdf`로 저장
- Kiro 설명: 8~9번 슬라이드, 총 70초

## 1. 표지 — 15초 (00:00~00:15)

나만의 냉장고는 혼자 사는 직장인과 대학생을 위한 냉장고 재고 관리 서비스입니다. 영수증이나 주문내역을 찍으면 재고가 채워지고, 추천받은 메뉴를 요리하면 사용한 재료가 자동으로 빠집니다.

## 2. 문제 — 30초 (00:15~00:45)

1인 가구는 양파 한 망이나 대파 한 단을 한 번에 쓰기 어렵습니다. 온라인 장보기에는 종이 영수증도 없습니다. 무엇보다 먹은 재료를 사용자가 직접 지우지 않으면 앱의 재고가 실제 냉장고와 달라집니다. 이 상태에서는 남은 재료 추천도 믿을 수 없습니다.

## 3. 해결 흐름 — 25초 (00:45~01:10)

해결 방법은 기능을 따로 제공하는 것이 아니라 하나의 흐름으로 연결하는 것입니다. 등록한 재료로 메뉴를 추천하고, 요리가 끝나면 사용량을 확인한 뒤 재고를 줄입니다. 이 흐름이 다시 정확한 추천의 기반이 됩니다.

## 4. 대표 차별점: 요리 후 자동 차감 — 45초 (01:10~01:55)

대표 차별점은 요리 후 자동 차감입니다. 추천 레시피에는 사용할 재료와 수량이 개수 단위로 들어 있습니다. 요리했어요를 누르면 양파 8개가 7개로 바뀌는 것처럼 차감 전후를 보여줍니다. 사용량은 0.5개 단위로 고칠 수 있고, 사용자가 확인해야만 재고에 반영됩니다. 같은 요청이 두 번 들어와도 요청 ID와 DynamoDB 트랜잭션으로 한 번만 차감합니다.

## 5. 영수증·주문내역 등록 — 30초 (01:55~02:25)

마트 영수증뿐 아니라 온라인 주문내역 캡처도 같은 버튼으로 등록합니다. Bedrock이 품목명, 개수, 보관 위치와 예상 소비기한을 추출합니다. 결과는 추정값이므로 사용자가 수정하거나 삭제하고 품목을 추가한 뒤 저장합니다. 중량 단위는 개수로 바꾸고, 큰 이미지는 브라우저에서 줄여 전송합니다.

## 6. 3일 식단 — 30초 (02:25~02:55)

한 끼 추천만으로는 양파 한 망 같은 대용량 재료를 다 쓰기 어렵습니다. 3일 식단은 점심과 저녁, 총 6끼에 재료를 나눠 사용합니다. 화면에서는 메뉴뿐 아니라 지금 수량과 3일 뒤 예상 잔여 수량을 보여줍니다. 각 끼니에서도 같은 레시피와 차감 흐름을 사용합니다.

## 7. AWS 구조 — 25초 (02:55~03:20)

프론트엔드는 React 정적 SPA로 만들어 S3와 CloudFront에 배포했습니다. 브라우저의 API 요청은 CloudFront를 거치지 않고 API Gateway로 직접 가며, Python Lambda가 FastAPI와 Mangum으로 처리합니다. 재고는 DynamoDB에 저장하고 이미지 인식과 추천은 Bedrock의 Claude Haiku 4.5가 담당합니다. 아래 배포 흐름은 GitHub OIDC 단기 자격 증명으로 SAM과 프론트엔드를 배포하는 구조입니다.

## 8. Kiro와 Figma MCP — 35초 (03:20~03:55)

Kiro 안에서 Designer와 Planner가 같은 Figma 파일을 역할별로 이어서 작업했습니다. Designer는 Figma MCP로 색상과 크기 변수, 공통 컴포넌트와 9단계 구현 화면을 만들었습니다. Planner는 그 화면 인스턴스를 재사용해 Screen Spec 7개 보드와 정상·오류 복구 프로토타입을 연결했습니다. 결과는 30개 프레임과 25개 reaction이며, get_screenshot으로 잘림과 연결 상태까지 검증했습니다. 슬라이드의 링크로 Figma 원본도 확인할 수 있습니다.

- Figma 원본: https://www.figma.com/design/E4LmR5L4WsyD8Knn7zZl6X/%EB%82%98%EB%A7%8C%EC%9D%98-%EB%83%89%EC%9E%A5%EA%B3%A0---Kirothon?node-id=24-147

## 9. Kiro: Steering에서 배포까지 — 35초 (03:55~04:30)

Kiro는 먼저 steering에 문제, 규칙과 범위를 고정하고 Requirements-First Spec으로 13개 요구사항, 156개 인수 조건과 23개 정확성 속성을 만들었습니다. 이후 Planner, Designer, Developer, Infrastructure 네 역할로 나눠 실행했습니다. MVP 기록에는 완료 작업 28개와 실행 68회가 남아 있습니다. 배포도 별도 Quick Spec으로 만들고 GitHub OIDC, 계정·리전·저장소·브랜치 검사까지 구현했습니다.

## 10. 검증과 마무리 — 30초 (04:30~05:00)

데모의 영수증 업로드, 결과 수정, 저장, 메뉴 추천, 레시피 확인, 재고 차감과 목록 반영을 종단 간 테스트로 검증했습니다. 핵심 데모 테스트 3개, 백엔드 81개와 식단 11개, 프론트엔드 48개와 식단 4개가 통과했습니다. TypeScript 검사와 프로덕션 빌드, SAM 검증, 실제 AWS 배포도 완료했습니다. 나만의 냉장고는 재료를 등록하는 데서 끝나지 않고, 요리 후에도 실제 냉장고와 맞는 재고를 유지합니다.
