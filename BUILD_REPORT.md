# BUILD REPORT

1인 개발, 6시간 안에 문제 정의부터 배포 자동화까지 Kiro와 함께 진행했습니다. 문제 정의와 규칙은 steering에 고정하고, 기획·디자인·구현·인프라는 역할별 custom agent와 두 개의 spec으로 나눠 진행했습니다.

## 개발 과정에서 바뀐 점

| 처음 계획                                   | 바뀐 결과                                                                                        | 이유                                                                                                                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 영수증으로 등록하고 메뉴를 추천받는 기능    | 요리 후 자동 차감을 대표 차별점으로 추가하고, 주문내역 캡처 인식과 3일 식단을 더했습니다         | 같은 조합의 앱이 이미 있었습니다. 기존 앱이 놓친 "빼는 일"과 온라인 장보기, 대용량 재료에 집중했습니다                                                 |
| 수량을 kg, g, 개 등 영수증 표기 그대로 저장 | 모두 개수로 바꾸고 0.5개 단위까지 허용했습니다. LLM 추정값은 모두 사용자가 고칠 수 있게 했습니다 | 영수증의 "양파 1.5kg"과 레시피의 "양파 반 개" 단위가 달라 차감할 수 없었습니다                                                                         |
| Next.js 하나로 구현                         | S3 + CloudFront 정적 SPA, API Gateway + Lambda, DynamoDB, Bedrock으로 바꿨습니다                 | AWS에 MVP를 올리고 실제 서비스를 운영한다는 가정이었습니다. 하루 몇 번 몰리는 트래픽에서 Lambda는 쓰지 않을 때 비용이 0이고, ECS는 ALB 고정비가 듭니다 |
| 3일 식단을 LLM 한 번으로 생성               | 메뉴와 사용 재료를 먼저 받고, 조리 단계는 끼니를 열 때 따로 생성합니다                           | HTTP API 30초 통합 제한 때문입니다                                                                                                                     |
| 3일 식단 3끼, 기본 양념 4종                 | 점심·저녁 6끼로 늘리고, 기본 양념은 8종으로 고정했습니다                                         | 3끼로는 양파 8개를 다 쓰기 어려웠습니다. 기획 에이전트가 낸 열린 질문의 추천안을 채택했습니다                                                          |
| 수동 배포                                   | GitHub OIDC 기반 CI/CD를 별도 spec으로 추가했습니다                                              | 액세스 키 없이 배포하고, 잘못된 계정·리전·브랜치로 배포되는 것을 막기 위해서입니다                                                                     |

## 어려웠던 점과 해결 방법

| 어려웠던 점                                                       | 해결 방법                                                                                                                                                         |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 비슷한 앱이 이미 많아 문제 정의가 약해질 수 있었습니다            | 웹 검색으로 앱스토어 설명을 비교했습니다. 비교표에는 확인된 기능만 O로 적고, 확인하지 못한 칸은 "설명에 없음"으로 구분했습니다                                    |
| LLM 응답 형식이 틀리면 화면이 깨집니다                            | Bedrock Converse API의 strict tool use로 JSON 스키마를 강제하고 Pydantic으로 다시 검증합니다. 검증에 실패하면 남은 시간이 8초 이상일 때만 한 번 교정을 요청합니다 |
| Lambda·HTTP API 30초 제한 안에 LLM 응답을 받아야 했습니다         | 요청마다 27초 deadline을 두고 SDK 재시도는 0회로 했습니다. 추천과 조리 단계를 나눠 호출하고, timeout이 나도 입력과 재고를 유지한 채 다시 시도할 수 있게 했습니다  |
| 휴대폰 사진이 Bedrock 이미지 3.75MB, Lambda 6MB 제한을 넘었습니다 | 브라우저에서 EXIF 방향을 반영해 긴 변 1568px 이하, 3,932,160바이트 이하 JPEG로 줄인 뒤 올립니다                                                                   |
| 차감 요청이 두 번 가면 재고가 두 번 줄어듭니다                    | 차감 기록 저장과 재고 갱신을 DynamoDB 트랜잭션 한 번으로 묶고, 요청 ID로 멱등성을 보장했습니다                                                                    |
| 테스트할 때마다 AWS를 호출할 수 없었습니다                        | 메모리 DynamoDB 어댑터와 시나리오별 Bedrock 고정 응답을 만들었습니다. 등록부터 차감까지 종단 간 흐름을 AWS 없이 검증합니다                                        |
| 커스텀 에이전트에는 steering이 자동으로 들어가지 않았습니다       | 에이전트 프롬프트에 작업 전 steering 파일을 직접 읽는 단계를 넣었습니다. Spec 세션에서는 `#steering:` 참조로 명시했습니다                                         |
